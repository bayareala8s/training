### Q-01-08

`Money.equals` should use which comparison, and why?

- A. `amount.equals(other.amount)`, because scale is part of the legal tender definition
- B. `amount.compareTo(other.amount) == 0`, so `10.0 USD` and `10.00 USD` are the same value
- C. `Double.compare(amount.doubleValue(), other.amount.doubleValue())` for speed
- D. `System.identityHashCode`, because each `Money` construction is unique

---

<details>
<summary>Answers</summary>

1. **B** — Major 65 is Java 21 bytecode. Point the process at a 21 JVM. Preview flags and Spring downgrades do not fix the class-file version.
2. **B** — SOLID: one reason to change (`Payment` is not a notifier), extend edges in `allowedNext()`, depend on `PaymentAuthorizer`. A always-approve double violates Liskov; a concrete SDK in the service violates Dependency Inversion. Constructor invariants still belong on `Money` (see Q-01-08).
3. **C** — Skipping `VALIDATING` / `AUTHORIZED` is illegal. The other three edges are documented.
4. **C** — Closed enums belong in `EnumSet`. String lists and raw lists accept mistakes; `Hashtable` is a leftover.
5. **B** — Frozen + valid money is a business decline, not a missing customer and not a swallowed success.
6. **B** — `orElse(null)` recreates null and can skip `belongsTo`. Use `orElseThrow` with `ACCOUNT_NOT_FOUND`.
7. **C** — Same key and different body hash is a conflict. Silent replay would lie about the amount.
8. **B** — `BigDecimal.equals` is scale-sensitive. Payments compare numeric value; `double` is not money.

</details>
