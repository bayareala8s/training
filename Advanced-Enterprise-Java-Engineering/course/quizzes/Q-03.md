### Q-03-08

Which test strategy actually proves BayPay’s payment write contract?

- A. `@WebMvcTest` that mocks `PaymentApplicationService` and asserts the controller returns `201`
- B. `@SpringBootTest` + MockMvc (`PaymentApiIT`) covering `201`, replay `200`, `409`, `422`, and missing-key `400` against H2
- C. A unit test that verifies `PaymentRepository.save` was called once
- D. Manual curl on local only, because Testcontainers is required for every assertion

---

<details>
<summary>Answers</summary>

1. **B** — Declare collaborators in the constructor. A locator hides the graph and blocks simple tests.
2. **B** — Same key and body is replay `200`. Do not post a second ledger row. `409` is a different body.
3. **B** — Bean Validation is `400`. Domain remaining-amount is `422` with a BayPay `code`.
4. **B** — Log the stack; generic `500` body. Do not leak SQL or turn bugs into `422`.
5. **B** — Posting joins the caller’s transaction. A propagating runtime exception rolls everything back.
6. **B** — Swallowed exceptions commit. That is how API success and a missing ledger coexist.
7. **B** — Database blip → not ready, still live. Do not restart-storm or publish heapdump.
8. **B** — `PaymentApiIT` is the money contract. Mocks and curl-only do not lock replay.

</details>
