# Q-02 — Module 2 quiz

**Module:** Advanced Java Concurrency  
**Questions:** 8  
**Case study:** BayPay Financial Services (fictional)

Answer on your own first. Answers and explanations are in the details block at the end of this file.

---

**1.** Thread A sets a non-volatile `boolean authorized = true`. Thread B spins `while (!authorized)`. Which statement is correct under the Java Memory Model?

- A. B is guaranteed to see `true` because the heap is shared.
- B. B may see `false` indefinitely; there is no happens-before edge.
- C. B will see `true` after at most one context switch.
- D. The read is a data race, so the JVM must throw `ConcurrentModificationException`.

**2.** BayPay stores `availableCents` as `volatile long` and two capture threads execute `availableCents -= amount`. What can happen?

- A. Both captures always see the latest value, so funds cannot be double-spent.
- B. Volatile makes the increment atomic, so this is safe.
- C. Both threads can read the same starting value and both write a too-large remaining amount (lost update).
- D. The second thread is specified to wait for the first volatile write to complete the entire compound update.

**3.** An in-memory idempotency map is a `ConcurrentHashMap`. The code does `if (!map.containsKey(key)) { map.put(key, id); post(); }`. Why can Harbor Bike Co still be charged twice?

- A. `ConcurrentHashMap` does not allow two threads to call `put`.
- B. `containsKey` + `put` is two operations; both threads can observe absence and both post.
- C. `ConcurrentHashMap` iteration is illegal and aborts one post.
- D. The map is concurrent, so the second post is defined to become a replay.

**4.** Which executor configuration is acceptable for parallel payment posting?

- A. `newCachedThreadPool()` so the sale can scale without a cap.
- B. `ThreadPoolExecutor` with a bounded queue and `AbortPolicy`, mapping rejection to a 503.
- C. `DiscardPolicy` so a full queue never bothers the HTTP thread.
- D. A single-thread executor that you also call `get()` on from the same thread.

**5.** A virtual thread calls a blocking HTTP authorizer inside `synchronized (ledgerLock)`. What is the main risk?

- A. Virtual threads cannot perform HTTP.
- B. The carrier can remain pinned for the I/O wait, collapsing concurrency to roughly the carrier count.
- C. `synchronized` is ignored on virtual threads, so the ledger corrupts silently.
- D. The JVM converts the lock into a `Semaphore` automatically.

**6.** Completions for payments and refunds drop to zero, CPU is idle, health is UP, JDBC is idle, worker threads are still alive. Which investigation is the best next step after logs?

- A. Increase the heap and assume GC thrash.
- B. Capture a thread dump and see who owns which monitors.
- C. Disable idempotency keys to improve throughput.
- D. Add more worker threads until CPU rises.

**7.** Which statement about BayPay idempotency under concurrency is correct?

- A. An in-memory `ConcurrentHashMap` is sufficient once two JVM instances serve authorize.
- B. A unique database constraint (plus a transactional post) is the multi-instance control; the heap map is at most a single-instance helper.
- C. `Idempotency-Key` is optional if the client promise is “at most once.”
- D. Returning HTTP 201 twice for the same key is always correct as long as amounts match.

**8.** A canary uses two locks. What policy prevents circular wait without requiring `tryLock`?

- A. Document and enforce one acquisition order on every path, or collapse to a single money lock.
- B. Take locks in whichever order the method reads first; order does not matter if locks are private.
- C. Make both locks `volatile`.
- D. Call `notifyAll` on each lock after acquire.

<details>
<summary>Answers (open after you attempt)</summary>

1. **B** — A shared heap does not imply visibility. Without a happens-before edge, B may cache `false` forever. Visibility bugs do not throw.

2. **C** — `volatile` publishes a single write. It does not make read-modify-write atomic. Two captures can interleave and lose an update.

3. **B** — Thread-safe single operations are not an atomic business method. Use `putIfAbsent` in-process and a unique database key in production.

4. **B** — Money work must be bounded and rejection must be visible. Cached pools and `DiscardPolicy` lose or explode capacity.

5. **B** — Java 21 intrinsic locks pin the carrier. Holding `synchronized` across I/O recreates a tiny platform pool.

6. **B** — Idle CPU plus no completions plus live workers is a waiting problem until proven otherwise. A dump shows owners.

7. **B** — Two pods do not share a heap. Persist the key. Two 201s with two ledger rows is a duplicate debit.

8. **A** — Circular wait is broken by a single lock or one global order. Privacy of the object does not prevent opposite acquisition orders.

</details>
